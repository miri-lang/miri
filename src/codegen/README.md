# Codegen

The `codegen` module is responsible for the final phase of compilation: **translating the optimized Mid-Level Intermediate Representation (MIR) into executable machine code.**

## Overview

Miri's codegen architecture is designed around pluggable backends. The current implementation uses [Cranelift](https://github.com/bytecodealliance/wasmtime/tree/main/cranelift) to emit native binaries.

The code generation phase maps MIR constructs directly into target-specific instructions. It handles memory allocation (stack and heap), function calling conventions, literal initialization (like strings), and native control flow bridging.

## Architecture

-   **Backend Traits**: The system is abstracted behind common traits to support multiple generation targets (e.g., Cranelift, LLVM, SPIR-V, CUDA, WebAssembly, etc.).
-   **Translator (`translator.rs`)**: The core loop that visits MIR Basic Blocks and issues backend API calls.
-   **Variables and Locals**: MIR locals (`_0`, `_1`, etc.) are mapped to backend stack slots or virtual registers.
-   **Members of a value held as its bytes (`cranelift/value_locals.rs`)**: Every load and store of a member — a field read, a copy, a clear, an optional's or enum's tag — goes through `load_at` / `store_at`, which fold any chain of `iadd` with an `iconst` under the address into the access's immediate offset. A member written by a copy and read back afterwards is then the same address value, offset and type both times, which is what Cranelift's alias analysis needs to forward the store to the load or drop a repeated load. Cranelift forwards only from the last store to a location's alias region, so of a copy's members only the one stored last is forwarded to a following read.
-   **Pass-through block parameters (`cranelift/pass_through.rs`)**: The translator seals its blocks only once every block is translated, so Cranelift's frontend gives a loop header a parameter for a variable the loop never writes, which every branch from inside the loop hands back unchanged, and never removes it. Each translated function then has every parameter of a reachable block that all incoming branches, its own back edges aside, hand one value replaced by that value, so a value computed from an outer loop's counter is invariant to an inner loop. Cranelift's own removal of constant parameters keeps such a parameter, since the value it stands for is another block's parameter.
-   **Function Declarations**: Miri functions are exported with defined signatures (`declare_func_in_func`).
-   **Runtime Execution**: The codegen automatically links to the `miri_rt` runtime for features requiring heap allocation (e.g., strings) or complex operations (I/O).
-   **Source locations**: Asked for a code map (`CraneliftOptions::code_map`, which `--emit lines` and `--profile` set), the translator marks each statement's and terminator's instructions with where its span starts: the body's `SourceId` and the byte offset, listed once in the function's table of source points (`cranelift/source_points.rs`), whose index is the instruction's `SourceLoc`; Cranelift keeps a location in 31 bits, so a table holds at most 2^31 - 1 points. A point of inlined code also names the point of the call it was inlined through, in the same table, so nested inlining forms a chain out to a line of the function itself. A span covering no text, or a body with no source, is synthesized and keeps the location before it. After each user function is defined, the runs Cranelift recorded are read back through that table and returned in `CompiledArtifact::code_map` as backend-neutral `FunctionCodeMap`s: the link symbol, the code size and `(start, end, source, source offset, inlined at)` runs, each run naming its own file and the calls it was inlined through, innermost first. Cranelift gives no location to a constant its optimizer moves out of a loop and re-creates in front of each use inside it, so a loop block can begin with code no run covers; the code map charges the unlocated code heading a machine block (read off Cranelift's block layout, which `machine_code_cfg_info` records for a code-map build without changing the machine code) to that block's first run, since such a constant belongs to the statement it feeds (`cranelift/code_map.rs`). Every other unlocated instruction is left to the run before it, as a line table charges it. The code map lists the functions in the order the backend was handed them, whatever order they were defined in. Codegen never reads source text; the pipeline turns offsets into lines. The locations change none of the machine code, and a build that does not ask sets none.
-   **Inlining policy (`cranelift/inliner/`)**: An optimizing build (`CraneliftOptions::inline`, set for every opt level above 0, `--release` and `--profile` included) translates every CPU body to CLIF first, then inlines small user functions into their callers through Cranelift's `Context::inline`. An unoptimized build instead translates, defines and drops one function at a time. The call graph is the direct references between user functions; Tarjan's algorithm, run in translation order on explicit stacks, visits each strongly connected component after the components it calls, so callees are inlined into first and every decision repeats exactly from build to build. Each function is defined as soon as its callees have been inlined into it, and a candidate's body is dropped as soon as nothing still to come can reach a call of it, so the object's functions come out in that bottom-up order while the CLIF listing, the code map and the profile function table keep the order the functions were handed in. A callee is inlined only when it is called by a direct `call`, is neither the entry point nor recursive (itself or through a cycle), verifies, holds no loop (no back edge in its CFG), has a signature identical to the call's, and is at most 48 instructions, or 120 when it has a single call site. Its own definition is still emitted, so a single-call-site callee costs a second copy of its body. A caller grows to at most four times its own size and never past 2000 instructions, with at most 512 bytes of added stack slots, or 128 for a caller that can call itself. Inlining runs in rounds: the calls a copy holds, those its callee kept because the callee's own budget could not afford them, are weighed in the next round against what is left of the caller's budget, with the same rules except that every callee is held to the 48-instruction limit there, since the copy holding the call may itself be copied many times, so a small helper's callee is inlined wherever the helper is copied into a caller that can afford both, and a callee holding a loop or calling itself still keeps its call. Each round leaves its copies whole so they are repaired, their locations included, before the calls they hold are inlined; the rounds end when one inlines nothing. A candidate's body is held while one of its direct callers is still to be visited or a held candidate's body still calls it, and is dropped as soon as neither is so (`inliner/lifetimes.rs`); a function that is no candidate is never copied, so the calls it holds keep nothing alive. A callee holding a loop is never inlined: its iterations dwarf the call around it, a copy of the whole loop per call site buys little, and measured on the benchmark workloads it showed no consistent gain.
-   **What is repaired after inlining (`cranelift/inliner/repair.rs`)**: Cranelift copies a callee's `Symbol` global values without translating their name reference, which indexes the callee's own table of external names, so each copied symbol is re-declared in the caller's table; one that cannot be resolved fails the build. It also copies no source locations. Cranelift numbers the caller blocks of a copy from the caller's block count, in the callee's block order, and fills each with its original's instructions in layout order, a `return` becoming a `jump` (which is why the Cranelift crates are pinned to one exact version, with a unit test that fails if an upgrade changes it); when every copied block lines up with its original opcode for opcode, each copy takes its original's source point re-listed as inlined through the call, and otherwise the call's own location.
-   **Slot promotion (`cranelift/slot_promotion/`)**: Once a function's callees are inlined into it, after the repairs above and before it is weighed as a candidate, the explicit stack slots it reaches only by plain native-order loads and stores at constant offsets are held as SSA values, so a value held as its bytes stays in registers across the inlined code rather than being stored and read back, which Cranelift's own store-to-load forwarding does for one store at a time. A slot's address may be offset by a constant (an `iadd` with an `iconst`, which is also what Cranelift's `iadd_imm` builders emit, as its `stack_load` and `stack_store` builders emit a `stack_addr` and a plain access), and block parameters are copy-propagated toward addresses first: a parameter whose every incoming value, other than itself along a back edge, is one slot address or one other block parameter is replaced by that value, as the frontend leaves a variable holding a slot's address in each loop header. Only addresses and parameters are propagated, since a parameter can be a link in a chain ending at an address and no other value can make a slot promotable; each round lets the next see an address derived from a forwarded parameter, and the rounds stop when one forwards nothing or after a fixed number. This, the removal of unreachable blocks and the resolution of aliases change a function that is looked at even when none of its slots is then promoted, without changing what it does. Each run of bytes every access covers whole is a cell, typed by its first float access or else its first access, the others converted by a same-width bitcast. A slot is left in memory when its address is used any other way (a call, a store as data, a comparison, a select, a return, an atomic, an extending load or a truncating store), when two of its accesses overlap without covering the same bytes, when an access reaches past it, when a cell may be read before it is written, when an access has a type other than an integer, `f32`, `f64` or a fixed vector of those, when a stack map names it, or when its cells times the function's blocks would pass a fixed bound, the slots with the fewest cells kept first. A function holding an exception table, reading the frame or stack pointer, switching stacks or naming a slot in a debug tag is left as it is. Each cell's liveness decides which blocks take a parameter for it; the blocks are rewritten in reverse postorder, each new instruction taking the location of the access it replaces, and a promoted slot is sized to nothing. The decisions depend only on the IR, so a build repeats exactly, and promoting a promoted function changes nothing. An unoptimized build defines its functions without inlining and so without promotion.
-   **Closure trampolines (`cranelift/closure_trampolines.rs`)**: A runtime function that calls a Miri closure is handed it together with the address of a trampoline (see the closure ABI in `src/mir/README.md`). Before any body is compiled, every trampoline the runtime calls name is emitted once, keyed by its shape: it loads the closure's code pointer, loads each argument the closure takes as a word out of the slot address it is handed or passes that address on, calls the closure and stores the result through the result address. Each closure is checked against its trampoline first — the signature the trampoline calls through must be the one the closure is compiled under — and a mismatch is a compile error. Every CPU backend must define each trampoline the bodies it compiles reference: the MIR names them as function operands, and nothing else emits them.

## Design Principles

1.  **Zero-Cost Abstractions**: The codegen aims to translate MIR directly to optimized machine code, keeping overhead minimal.
2.  **Safety via Runtime**: Safe constructs like strings and arrays are backed by a lean runtime library, dynamically linked or statically compiled.
3.  **Explicit Memory Management**: Generates all necessary drops/deallocations injected during MIR optimizations (Perceus RC).

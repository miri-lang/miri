
## 2026-07-07 - [Integer literal overflow silently truncated to i64]
**Bug:** A bare integer literal larger than `i64::MAX` (e.g. `999999999999999999999999999999`) type-checked fine and silently produced a garbage i64 value at runtime instead of a compile error.
**Root cause:** `TypeChecker::infer_literal` (`src/type_checker/expressions/literals.rs`) returned `TypeKind::Int` (i64) for *every* integer literal regardless of magnitude. The parser (`literals.rs`) parses into `i128` and `ast::int()` picks the smallest fitting variant (up to I128), so oversize values survived to MIR/codegen, which truncated i128→i64. The type checker was the layer that should have rejected them.
**Lesson:** Two traps here. (1) `i64::MIN` can only be spelled `-9223372036854775808`, whose bare operand `2^63` is one past `i64::MAX`; a naive parse-time range check breaks it — the negation must relax the bound by one. (2) `i128`/`u64`/`u128` are real annotatable types (`let x i128 = <big>`), so a blanket i64 check falsely rejects them; scope the check to the default-`int` case via an exemption set. Note: wide-int *large literals* still truncate at runtime (i128 codegen is a separate, pre-existing bug — the passing `test_integer_large_literal` only checks types, a green-washer).

## 2026-07-07 - [Shadowing let initializer read the new binding, not the outer]
**Bug:** `let x = 5` then `let x = x + 100` produced `100`, not `105`; likewise a loop body `let i = i + 100` read `0`/previous-shadow instead of the loop value. The shadowing binding's own initializer read the not-yet-assigned new local.
**Root cause:** MIR lowering — `LoweringContext::push_local` inserted the new name into `variable_map` *before* `lower_single_variable` lowered the initializer (and DPS even lowered the RHS directly into the new zero local). So the identifier in `x + 100` resolved to the local being declared. Lived in `src/mir/lowering/context.rs` + `variable.rs`, not the type checker (which correctly type-checks shadowing).
**Lesson:** A binding must not be resolvable during evaluation of its own initializer. When a declaration allocates its slot before lowering the RHS, split "allocate + StorageLive" from "make the name resolvable" and bind the name only after the initializer is lowered. Watch for this any time DPS lowers an initializer into the freshly-declared local. The type-checker shadowing tests were green — the runtime path was untested (green-washing gap).

## 2026-07-07 - [Deep expression chain overflowed the compiler stack — fixed with a big-stack worker thread]
**Bug:** `1 + 1 + ... + 1` (~3500+ terms release, ~2000 debug) aborted the compiler with `thread 'main' has overflowed its stack`. Postfix method-call chains (`a.f().f()...`) crashed the same way. Type inference and MIR lowering both recurse on expression-nesting depth; the parser builds a long left-associative chain into a deep left-leaning AST.
**Why the obvious fix was wrong:** Charging the iterative binary loop (`Parser::binary_expression_precedence`) against `enter_recursion`/`MAX_PARSE_DEPTH` (256) stops the crash but breaks the intentional test `test_very_long_chain_of_binary_operators` (asserts a 500-op chain PARSES). 256 is the parser's stack-hungry *recursive-frame* budget; iteratively-parsed chains have a different, much higher safe ceiling. No magic-number cap cleanly clears 500 and stays below the crash.
**Fix (shipped):** Run the whole CLI command on a worker thread with a 512 MB stack (`src/main.rs`, `run_command`). This is how rustc handles deep recursion. Covers every path (run/build/check/test) and every integration test (they invoke the `miri` binary as a subprocess). `Cli` is `Send + 'static` so `thread::Builder::spawn(move || run_command(cli))` compiles; spawn failure propagates via `?` and a worker panic via `resume_unwind`. NOTE: `stacker::maybe_grow` was tried first and did NOT work — on the *main* thread it can't read the stack bounds, so it became a no-op (and added per-call overhead). stacker only helps on a thread with a known stack size; a big fixed stack is simpler and needs no dependency.
**Lesson:** A parser recursion-depth guard only protects stages that recurse on the *same* structure; an iteratively-parsed rule that still builds deep AST just relocates the overflow two stages downstream (no backtrace on overflow — localize by phase: `check` vs `build`). For unbounded-but-valid recursion depth, give the compiler a big stack rather than capping input (which breaks deep-input-is-supported contracts). Residual: a 512 MB stack still has a ceiling (~100k+ levels); truly adversarial megabyte-scale nesting would need a separate source-size/token limit.

## 2026-07-07 - [Wide-int literals green-wash wrong values — do NOT "fix" the cast rejection]
**Trap:** `18446744073709551615 as u64` (and `<big> as i128`) is rejected by the iteration-1 range check with "out of range for the default int type (i64)". Tempting to exempt cast targets like the variable-annotation exemption does — DON'T. The wide-int literal CODEGEN is broken: `let x u64 = 18446744073709551615` (already exempted) compiles but prints `-1`; `let x i128 = <i128::MAX>` prints `-1`. So exempting the cast makes it compile-and-print-`-1` — a SILENT MISCOMPILE, the exact thing iteration-1 exists to prevent. The rejection is the safe behavior (pre-iteration-1 it also printed -1; iteration-1 turned wrong-value into a compile error, an improvement).
**Root cause:** `infer_literal` types every integer literal as `Int` (i64); values > i64 are truncated in MIR/codegen. Literals wider than i64 are not representable end-to-end. The iteration-1 variable-annotation exemption (`wide_typed_int_literals`) green-washes this — it should really reject too, but that breaks the green-washing `test_integer_large_literal` (types-only) and is a contract call.
**Lesson:** The real fix is expected-type-directed literal typing + wide-int constant materialization in codegen (a feature, not a one-liner). Until then, prefer REJECTING wide-int literals over accepting-and-truncating. Any exemption that lets a >i64 literal compile is a silent-miscompile risk. See [[Integer literal overflow silently truncated to i64]].

## 2026-07-07 - [f-string escaped braces kept their backslash]
**Bug:** `f"\{literal\}"` printed `\{literal\}`, not `{literal}`. The escape correctly stopped `\{` from being read as an interpolation, but the backslash leaked into output.
**Root cause:** Split responsibility across two stages that disagreed on the escape set. The lexer (`src/lexer/formatted_string.rs::find_next_unescaped_brace`) treats `\{`/`\}` as escaped (text, not a delimiter), but `unescape_string` (`src/parser/literals.rs`) had no `\{`/`\}` arm, so its `Some(other)` fallback re-emitted the backslash. `\n`/`\t` worked, hiding the gap.
**Lesson:** When one stage *recognizes* an escape and a later stage *strips* it, they must cover the same escape set. Any escape the lexer treats specially must have a matching arm in `unescape_string`, or the backslash survives to output. Check both when touching string escapes.

## 2026-07-07 - [Hex/bin/oct bit-pattern literals wrongly rejected as out-of-range]
**Bug:** `0xFFFFFFFFFFFFFFFF` (all-ones mask) and `0x8000000000000000` (sign bit) errored "out of range for the default int type (i64)". These are the conventional bit-pattern / -1 idioms and pre-existing code relied on them.
**Root cause:** The integer-literal range check (added for DECIMAL overflow) is applied in the type checker's `Literal` arm, which can't see the radix — the AST has already discarded whether the literal was hex vs decimal. So the signed-decimal bound (i64::MAX) was wrongly imposed on hex/bin/oct too.
**Fix:** Reinterpret at the PARSER (`integer_literal`, src/parser/literals.rs), where the radix token IS known: a hex/bin/oct value in `(i64::MAX, u64::MAX]` becomes its signed i64 two's-complement (`value as u64 as i64`), so `0xFFFF…F` → `-1` (a value codegen represents natively). Decimal is untouched and stays range-checked.
**Lesson:** A magnitude/range check that must behave differently by *radix* (hex = bit pattern up to u64::MAX; decimal = signed value up to i64::MAX) belongs where the radix is still known — the parser — not the type checker, which sees only the resolved i128. Contrast the cast case (`<big> as u64`, journaled above): there accepting produces a WRONG value so rejection is right; here `-1` is the CORRECT value so accepting is right. The discriminator is "can codegen represent the intended value."

## 2026-07-07 - [Struct method (non-drop) triggers an ICE at codegen]
**Bug:** `struct P { v int; fn get() int: return self.v }` (method defined, even if never called) aborts with `Code Generation Error: MIR lowering failed for P_get: Could not determine the type of this expression. This is an internal compiler error — please report it.`
**Root cause:** `check_struct` (src/type_checker/statements/declarations/struct_def.rs) uses the `methods` list ONLY to compute `has_drop` — it never type-checks the method bodies. But codegen still emits `P_get`, and MIR lowering reads expression types the type checker never recorded → ICE. Struct methods also have no call dispatch (`p.get()` → "no field"), so they never worked. Classes have full method machinery (`check_class_collect_members` + `check_class_method_bodies` + method registry); structs have none.
**Fix:** Reject any non-`drop` struct method at definition with a clear error (structs are data types; behavior goes on a class / trait / free function). This kills the ICE without pretending to add the class-only feature. `fn drop(self)` stays allowed.
**Lesson:** When a stage COLLECTS a construct for codegen but a sibling type-checking path is only PARTIALLY wired (here: only drop-detection), you get an ICE at the downstream stage rather than a clean rejection. If a language construct isn't fully supported, reject it at the earliest stage that knows the type context — don't let half-built MIR reach lowering. Grep pattern: `methods.iter().any(...)` that ignores the bodies is a smell.

## 2026-07-07 - [OPEN/DEFERRED: Closures stored in a collection leak (multi-layer half-built)]
**Bug:** A closure stored in a `List` leaks its heap allocation on drop — `let fns = List([fn(x int) int: x + 1])` reports `MIRI_LEAK_CHECK: leaked 1 closure allocation(s)`. Leaks even if never called; also via `List<fn(int) int>()` + `push`. Plain-var closures (`let f = fn...`) are freed fine.
**Root cause (partial):** `classify_element_shape` (src/codegen/cranelift/predicates.rs) maps `TypeKind::Function` → `ElementShape::Other` → no `elem_drop_fn`, so a closure element is never dropped when the collection frees. BUT fixing only that is NOT enough: instrumentation showed `classify_element_shape` is **never even called with `Function`** for a closure element — the collection element-type resolution upstream (empty `List<T>()` construction, `List([..])` literal via an intermediate array, and `push`) does not propagate the closure's `Function` type to the drop-fn-setting sites. So the element type is lost before classify. It's a *multi-layer* gap, not a one-liner.
**Attempted & reverted:** Added `miri_rt_closure_drop_element` (runtime, mirrors `emit_drop_closure`: dtor→free_track→libc::free), an `ElementShape::Closure` variant, and wired classify/elem_decref. Runtime symbol linked but the leak persisted (classify never reached with Function). Reverted cleanly — didn't ship a partial fix in the codebase's most double-free-prone area.
**Danger noted:** A closure moved into a collection is NOT consumed (`f` still usable after `List([f])`) yet its source-drop is suppressed (all cases leak, none double-free) — de-facto single-owner. Any element-drop must keep source-drop suppressed or it double-frees. Captured-managed closures balance because captures are IncRef'd at capture; the element-drop must run the closure dtor exactly once.
**Next pass:** Fix element-type propagation for `Function` across the three collection-construction paths FIRST (so classify sees Function), then wire the element drop. Verify with the full `memory` suite + adversarial sharing/used-after/captured-managed cases. Needs a dedicated pass, not a Scout one-bug slot.

## 2026-07-13 - [Unsigned 64-bit values printed as negative — signed to-string, NOT truncation]
**Bug:** `let x u64 = 18446744073709551615; println(f"{x}")` printed `-1`; any u64 >= 2^63 formatted as its signed-i64 reinterpretation. But `x / 2` = 9223372036854775807, `x > 5` = true — storage, udiv, and unsigned compare were all correct.
**Root cause:** `emit_to_string` (src/mir/lowering/expression/mod.rs) cast EVERY integer type to `TypeKind::Int` (i64) and called `miri_rt_int_to_string(i64)`, which does signed `.to_string()`. u8/u16/u32 survived only because they zero-extend to a positive i64; u64/u128 >= 2^63 kept their bits and printed negative. Fix: added `miri_rt_uint_to_string(u64)` and routed unsigned types to it (bit-preserving cast, reinterpret as u64).
**Lesson:** This CORRECTS the earlier journal claim (["Wide-int literals green-wash wrong values"]) that `let x u64 = <max>` printing `-1` was a truncating-codegen SILENT MISCOMPILE. It was NOT — the u64 round-trips through arithmetic fine; only the *display* path was signed. When an unsigned value prints negative, probe it with udiv/compare BEFORE concluding the value is corrupt: a signed formatter is a display bug, truncation is a storage bug, and they need fixes in different stages. Untyped hex bit-pattern literals (`0xFFFF…F` → `int` → `-1`) are a separate, correct case — they are signed `int`, so the unsigned routing must key off the *type kind*, not the value.

## 2026-07-13 - [f32 printed with f64 promotion digits; two tests green-washed it]
**Bug:** `let x f32 = 0.1; println(f"{x}")` printed `0.10000000149011612`, not `0.1`. Any f32 whose value isn't exactly representable rendered its f32→f64 promotion error.
**Root cause:** `emit_to_string` (src/mir/lowering/expression/mod.rs) promoted F32 to f64 via `Rvalue::Cast` and called `miri_rt_float_to_string(f64)`. `f64::to_string()` then emits the *shortest round-trip for the f64*, which for a promoted f32 is the long form. Fix: added `miri_rt_f32_to_string(f32)` (formats from the f32 directly, keeping the whole-number `.1` convention) and routed F32 to it with no promotion.
**Lesson:** TWO green-washers hid this. (1) `assert_runs_with_output` is a **substring** match, so a test asserting `"0.1"` PASSES against `"0.10000000149011612"` — pin the whole rendering with sentinels (`f"[{x}]"` / expect `"[0.1]"`) whenever the wrong output is a superstring of the right one. (2) `math::integer_math::test_{min,max}_float_still_works` literally asserted the buggy long forms (`9.899999618530273`), codifying the defect as expected behavior — a test that encodes a promotion artifact as its oracle is a bug marker, not coverage. Same shape as the u64 signed-formatting fix earlier today: per-width to-string helpers keyed off the MIR TypeKind, never a widen-then-format shortcut.
